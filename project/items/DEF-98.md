# DEF-98 — Restore drops the background and custom images

## Intent

A session that browser recovery restores opens on a blank canvas: the route, its waypoints and its crowds come back, and the background they were placed on does not. Custom images are lost too: a waypoint's custom marker comes back as a dot and a custom path head as the arrow (`stripAssetReferences`, `src/app/persistence.js` (:613–634)). Recovery is model-only by design: its snapshot keeps the route model and clears the image fields it knows, so it keeps no image's bytes or file name (:636–668); the extra fields a crafted file can add survive, a known exception on the wish list, and start-up loads the default map only when nothing was restored (`src/app/startup.js` (:14)). So even a background the app ships comes back white: the default map, an Example Backgrounds image, or an example project's own (`src/examples/index.js` (:196–226)). Nothing on screen says so. The omission notice goes only to the screen-reader announcer (`index.html` (:18), `sr-only`), once per project opened, restored or cleared (`src/app/persistence.js` (:678–693), (:1126–1131)), when its first autosave leaves an image out; an ordinary restore then says "Previous session restored". A record from before the model-only rule that still holds a background's bytes is restored with it once, then rewritten without it (:505–510), (:1516–1531), so that background is lost at the next reload. Waypoints are stored as normalised image coordinates (`src/utils/imageCoordinates.js`), so the only background that fits a restored route is the one it was made on. The owner met it in use on 2026-10-13 and chose that recovery keeps every image, within feasible limits, with a warning that names the file and says why whenever one is not kept, and that it is done as soon as possible. This supersedes the model-only boundary for images (the decisions, DEF-98). **P1**

## Acceptance criteria

- A session restored from browser recovery shows every image the live project references, with the route where it was on them, within the limits below:
  - the background, bundled (the default map, an Example Backgrounds image, an example project's) or uploaded (PNG, JPEG or WebP), at the same fit, overlay and zoom;
  - each waypoint's custom marker image;
  - the custom path head.
- Recovery keeps each image's file name with it.
- The limits are stated in README's Auto-save section: per image and in total, in bytes, count and decoded pixels, and no larger than a project file's (`src/services/ImageAssetService.js` (:23–31), `src/models/ImageAsset.js` (:5–12)). Images reachable only through undo history are not kept, as exports drop them (DEF-23).
- When the images together exceed what recovery can hold, which are kept is decided by a stated order, the background first; the rest are warned of as below.
- After that restore, Save Project and the ZIP and HTML exports carry the images as they would had they been chosen in this visit (`getRetainedBackgroundDataURL`, `src/app/persistence.js` (:578–605)).
- A record that still holds image bytes, from before the model-only rule, keeps them through its restore: the background, custom markers and custom path head survive a second reload.
- Whenever recovery does not keep an image, a warning on screen, announced as well, names the file and says why it was not stored. Examples: over the limits, refused by the browser's storage, lost from it since, or a record from before the fix. The warning is given when recovery is written and again at the restore. The warning names the file wherever its name survives. Where the name was kept and has since been lost from the browser's storage, the warning says that. A model-only record from before the fix keeps no image references at all (`src/app/persistence.js` (:613–650)), so it cannot say which images it had: its restore says that recovery before this release kept no images, and names none. When the whole recovery point is gone, nothing can say what it held, and the app starts as on a first visit (:1490–1491).
- A background that cannot come back is offered on screen with a way to choose it again, its file name where the name survives, and the reason, as above. The restore never puts another image in its place. A custom marker or path head that cannot come back keeps today's built-in fallback, named in the warning.
- Recovery is never reported as kept when it was not, and a recovery point never pairs the route with images from another state.
- An image recovery keeps raises no omission warning (`reportAutosaveOmissions`, `src/app/persistence.js` (:678–693)).
- Clear All removes the kept images and their names with the rest of the recovery point, and stops any write of them still pending. A cleared image cannot return on reload, by a late write or by undo. Clear All's non-undoable empty baseline and a restore's history reset stay as they are (`src/app/projectReset.js` (:102–113); `src/app/persistence.js` (:1106)).
- The documents that state the model-only boundary state the new one:
  - `project/brief.md` (:97–98);
  - README's Auto-save section (:142–146) and its pitfall line (:343–345);
  - the comments in `src/app/persistence.js` (:636–640) and `src/app/backgroundLoading.js` (:101–102), (:145).
- A regression test fails before the fix and passes after it. An uploaded background, a bundled one, a custom marker and a custom path head are each autosaved, and the app is booted again from that record: each image comes back at the same size, with its file name, and the waypoint's marker style and the path head's style are custom again. An image over the per-image limit, and images over the total, are each not kept, and the warning names each one and the reason.
- No new dependency (the rules: jszip and mediabunny only).
- Every existing test stays green; none is deleted, skipped or weakened.
