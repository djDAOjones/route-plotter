# recall — the record's self-test

At phase close, read the record alone and answer with paths and entry
headings. A separate fresh session is stronger evidence; a check in
this session is local and must be labelled that way. Never imply that
local recall proves a handoff to another model or harness.

1. What were the last four pieces of work shipped, in order?
2. Name one decision from this phase and why it was made.
3. What is currently deferred, and where is it recorded?
4. What is the next open item, and which phase contains it?

Score each 0, 1 or 2: 2 means supported with the why or where; 1 means
partial; 0 means missing. If fewer than four items have shipped, naming
all of them and stating that limit can score 2. If none are deferred,
or no next item exists, cite the empty list and the owner-direction
record. This is an audit of the record, not a memory guessing game.

First produce the answers without editing. Then the sole writer stores
one result in the trajectory, including four components and mode:

```text
- RECALL — 8/8 (YYYY-MM-DD) — scores: 2,2,2,2 — local — see decisions
```

Use `fresh` only for a separate session with no prior task context.
Store the answer anchors and, for a score below 2, the missing fact and
repair in the phase-close decision. Keep the original result before
repair; a later recheck is a separate line. Check and commit after this
write, as the close verb specifies. The validator checks the arithmetic
and shape; the reader judges whether each answer is supported.
